# Список предложений в боте: «Берём» вместо простоя — дизайн

Дата: 2026-10-25. Статус: одобрен владельцем 2026-10-25. Целевая версия комплекта: 0.7.0.

## Зачем

Ночью 25.10 оба прогона emmett-brown прошли впустую: одобренных изменений не было, а владелец запретил команде самой планировать кандидатов из бэклога проекта. Бэклог живёт в документе проекта (у emmett-brown — `SHARED-UNDERSTANDING.md` §4.1), в Telegram его не видно. Владельцу неоткуда выбрать следующую работу, команде неоткуда её взять — работа встаёт. Днём это случается чаще, чем ночью: ручных прогонов днём больше, и задачи кончаются именно тогда.

Цель: в боте всегда есть короткий список того, что можно сделать дальше, — кандидаты владельца и идеи команды. Владелец выбирает пункт одной кнопкой «Берём», команда на следующем прогоне присылает план простыми словами, владелец одобряет или отклоняет его прежними кнопками.

Критерии успеха:
- когда одобренной работы нет, прогон не заканчивается впустую: он пополняет список предложений;
- в боте по кнопке «💡 Предложения» видно 5–7 лучших пунктов с ответом «что это даст» и пометкой, чья идея;
- от «Берём» до плана на одобрение — один ближайший прогон, без участия владельца сверх нажатия;
- через месяц список не превратился в очередь дел для владельца.

## Решения владельца (2026-10-25)

1. В боте показывается список: кандидаты владельца из бэклога проекта и предложения команды — какой функционал добавить, какие места отполировать, лучшие практики похожих систем, удобства. У каждого пункта пометка, чья идея.
2. Владелец выбирает пункт кнопкой «Берём». Команда готовит план простыми словами: как будет работать и что даст. Дальше — одобрить или отклонить (существующие кнопки одобрения изменений).
3. После «Берём» пункт ждёт следующего прогона — ночного или по «Запусти». Сам прогон кнопка не запускает.
4. Команда пополняет список понемногу в каждом прогоне, а не только когда работа кончилась.
5. Источники идей: интернет (как делают похожие системы), собственные знания команды, код и отчёты проекта, заметки владельца. Владелец может накидывать идеи заметками в боте.
6. Анти-цель: обилие пунктов, которые требуют от владельца действий.
7. Владелец подтвердил догадки сессии:
   - от владельца пункт требует ровно одного нажатия «Берём»; всё сверх этого (прод, секреты, деньги, спорное решение) пункт называет прямо строкой «от вас понадобится: …»; таких пунктов мало, они идут в конце списка;
   - видны 5–7 лучших пунктов, остальное — по кнопке «ещё»;
   - отклонённое не всплывает снова, если у команды нет новых доводов;
   - пункт без «Берём» не устаревает и сам не запускается: правило «молчание — согласие» к списку не применяется;
   - это возможность комплекта mcfly для любого проекта, а не только для emmett-brown;
   - сначала работа, потом идеи: идеи ищутся после основной работы прогона или когда работы нет; одобренное изменение ради идей не откладывается;
   - немного за раз: до 2 новых пунктов за прогон и небольшая доля времени прогона; если работы нет совсем — больше, но с потолком;
   - каждый пункт заполнен одинаково и просто: что, зачем (что даст), откуда идея (бэклог владельца, заметка, код и отчёты, похожие системы — со ссылкой), примерный размер, «от вас понадобится: …»;
   - без дублей: перед добавлением команда сверяет пункт со списком, бэклогом и отклонёнными;
   - бэклог владельца — первым; его пункты не переписываются по смыслу, а показываются как есть с пометкой «ваш».
8. Ответы после проверки документа (25.10):
   - **«Отклонить» в Telegram значит только «не сейчас».** Пункт (или план по взятому пункту) уходит в список «обсудить в сессии» — его владелец разбирает с Claude в сессии, не в Telegram. Окончательный отказ тоже даётся только в сессии. В Telegram окончательного отказа нет.
   - **План по взятому пункту молчанием не одобряется.** Авто-одобрение по сроку к таким изменениям не применяется — только кнопка «Одобрить».

## Не цели

- Автоматический старт работы без «Берём». Пункт списка сам по себе ничего не запускает и не одобряет.
- Обсуждение пункта в боте перед «Берём» (диалог, уточнения). Уточнять владелец может заметкой; это не часть кнопок.
- Замена `mcfly/goals.md` («🎯 Цели»). Цели — веха и чек-лист владельца; список предложений — что делать дальше.
- Разбор произвольного документа бэклога кодом комплекта. Документ проекта читает команда (модель), не `src/`.
- Изменение правил одобрения обычных изменений OpenSpec (сроки авто-одобрения, категории) — остаются как в 0.6.3; меняются только изменения, созданные по пункту списка (`mcfly.idea`).
- Окончательный отказ и обсуждение пунктов в Telegram — только в сессии владельца с Claude.

## Как это устроено

### Файл списка: `mcfly/ideas.yaml`

Один файл на проект, в git, рядом с `questions.yaml`; добавляется в служебные пути runner'а (`STATE_PATHS`), чтобы коммититься вместе с ответами и отчётами. Пишут его бот (новая идея владельца, «Берём», «Не надо») и прогон команды (новые пункты, перевод в «спланировано»).

Пункт:

| Поле | Что это |
|---|---|
| `id` | `I1`, `I2`, … — сквозная нумерация, как у вопросов `Qn` |
| `title` | что предлагается, одной строкой простыми словами |
| `benefit` | что это даст владельцу или пользователям продукта, 1–2 предложения |
| `how` | как примерно будет работать, 1–2 предложения (необязательно для идей владельца) |
| `source` | `owner-backlog` (бэклог проекта), `owner-note` (заметка владельца), `team` (код, отчёты, знания команды), `research` (похожие системы) |
| `ref` | откуда взято: ссылка на место бэклога («SHARED-UNDERSTANDING §4.1 п. 9»), id заметки, файл, URL для `research` (обязателен для `research`) |
| `size` | `S` / `M` / `L` — примерный размер (меньше дня, день-два, больше) |
| `needs_owner` | что понадобится от владельца сверх «Берём», или пусто |
| `status` | `proposed` → `taken` (нажато «Берём») → `planned` (создано изменение) → `done` (изменение заархивировано); `discuss` — «не сейчас» из Telegram, ждёт разбора в сессии; `rejected` — окончательный отказ, ставится только в сессии |
| `change` | имя изменения OpenSpec после планирования |
| `discuss_note` | причина «не сейчас», если владелец её дал; при отказе плана — из какого статуса и какое изменение отклонено |
| `reject_note` | причина окончательного отказа (из сессии) |
| `created_at`, `run_id`, `decided_at` | когда и кем добавлено, когда решено |

Отклонённые (`rejected`) и отложенные (`discuss`) пункты остаются в файле: по ним команда проверяет дубли. Пункт `rejected` может вернуться только новым пунктом с полем `new_arguments` — что изменилось с отказа (новая причина, новые данные); без него команда такой пункт не добавляет. Пункт `discuss` команда не трогает и не дублирует: решение по нему — в сессии.

**Разбор в сессии.** CLI для сессии владельца (не для команды): `mcfly ideas list [--status …]` — пункты с полями; `mcfly ideas set <Iн> proposed|taken|rejected [--note …]` — вернуть в список, взять или отказать окончательно. Команда в прогоне эти переходы не делает, кроме `taken → planned` и `planned → done`.

### Бот

**Кнопка «💡 Предложения»** в постоянной клавиатуре (рядом с «🎯 Цели»), команды `/ideas`, «предложения», «идеи». Показывает:

1. сначала пункты `taken` и `planned` — одной строкой каждый («⏳ I4 — ждёт прогона», «📝 I4 → изменение `foo`, ждёт одобрения в «Статусе»»);
2. затем `proposed`, не больше 7: сначала `owner-backlog` и `owner-note`, затем идеи команды; внутри групп — без `needs_owner` раньше, чем с ним, затем по возрастанию размера; пункты с `needs_owner` всегда в конце группы;
3. кнопка «ещё», если пунктов больше.

Пункт выводится так:

```
💡 I7 · ваш · M
Автозапуск обработки новых релизов
Что даст: документация не отстаёт, если вы забыли /release.
Откуда: SHARED-UNDERSTANDING §4.1 п. 7
[✅ Берём I7] [⏸ Не сейчас]
```

У пункта с `needs_owner` добавляется строка «🙋 От вас понадобится: …». Внизу экрана — строка «🗣 Обсудить в сессии: N» (пункты `discuss`), без кнопок.

**Кнопки** — новые префиксы `callback_data` по образцу `ap:`/`rj:`: `ib:I7` → текст «берём I7», `ix:I7` → «не сейчас I7», `il:2` → «предложения 2» (страница). «Не сейчас» переводит пункт в `discuss` сразу; причину владелец может дописать ответом на сообщение (как ответ на вопрос). Повторное «Берём» по `taken` — безвредно, ответ «уже взято».

**Отказ плана по взятому пункту.** Изменение OpenSpec, созданное по пункту, несёт в `.openspec.yaml` признак `mcfly.idea: I7`. Кнопка «Отклонить» под таким изменением в «Статусе» значит «не сейчас»: изменение получает `approval: rejected`, пункт — `discuss` с `discuss_note` («план отклонён в Telegram: <изменение>, <причина>»). Команда такое изменение **не перерабатывает** (в отличие от обычных отклонённых), пока в сессии не решат: вернуть пункт в `taken` (команда переделает план по заметке) или отказать окончательно (`rejected`; изменение удаляется сессией). Подпись кнопки для таких изменений — «⏸ Не сейчас» вместо «Отклонить».

**Идея владельца заметкой.** Сообщение, начинающееся с «идея:» или «💡», бот сразу записывает пунктом `proposed`, `source: owner-note`, `title` — первая строка, остальное — в `benefit`; отвечает «💡 I8 записал в предложения». Прочие заметки — как раньше. Следующий прогон может дополнить у такого пункта `how` и `size`, не меняя смысла.

**«📍 Статус».** Если одобренной работы нет, строка «Следующий прогон» говорит об этом и предлагает: «💡 Предложений N (ваших K) — выберите в «Предложениях»» с кнопкой. Пункты `taken` попадают в план следующего прогона («Следующий прогон: план по I7»).

**Утренняя сводка.** Если одобренной работы нет — та же строка с кнопкой. Новые пункты прогона перечисляются в отчёте («Новые предложения: I9, I10»).

### Прогон команды (`prompts/run.md`, скиллы, агенты)

Шаг 2 «Фронт работ» меняется:

- a. Одобренные изменения с открытыми задачами → реализация, как сейчас.
- b. Нет одобренных, но есть пункты `taken` → планировщик создаёт изменение по самому старому `taken` (не больше `max_changes` за прогон). Первый раздел `proposal.md` — «Простыми словами»: как будет работать, что даст, что понадобится от владельца. В `.openspec.yaml` — `mcfly.idea: <Iн>`. Затем `openspec validate --strict` и `mcfly approval request`; пункт → `planned`, поле `change`. Дальше — поток одобрения, но **без авто-одобрения по сроку** (см. ниже).
- c. Нет ни того, ни другого → **новые изменения сами не планируются**; прогон пополняет список (шаг «Предложения» ниже) с повышенным потолком и завершается отчётом. Отклонённые изменения с `mcfly.idea` не перерабатываются (решение — в сессии); обычные отклонённые, как и раньше, перерабатывает планировщик.
- Если одобренная работа есть, а пункт `taken` ждёт: после интеграции (шаг 5), когда до дедлайна остаётся не меньше 30 минут, планировщик создаёт план по одному `taken` в том же прогоне; иначе — в следующем. Такое планирование не входит в `max_changes` (лимит реализаций).

**Одобрение планов по пунктам.** `isAutoApprovable` возвращает false для изменений с `mcfly.idea`: `expireApprovals` их не трогает, «Статус» не показывает срок авто-одобрения («ждёт вашего решения, само не одобрится»).

Новый шаг «Предложения» — после интеграции и до отчёта (между шагами 5 и 6), а также вместо работы в случае c:

- потолки: обычный прогон — до 2 новых пунктов и до 10 % времени прогона; прогон без работы — до 4 пунктов и до 25 % времени; в обоих — пропуск, если до дедлайна меньше 20 минут;
- источники по порядку: бэклог владельца (место задаёт проект, см. настройки) — перенести в список все ещё не перенесённые пункты как есть, `source: owner-backlog`, со ссылкой, без пересказа смысла; **перенос бэклога в потолок пунктов не входит** (это не новые идеи) — в первом прогоне переносится весь бэклог; пункты, которые бэклог помечает сделанными или запрещёнными к планированию, не переносятся или переносятся с пометкой; затем идеи команды по коду, отчётам eval/прогонов, повторяющимся замечаниям ревью; затем поиск похожих систем в интернете (`research`, со ссылкой);
- каждый пункт проверяется на дубли по `ideas.yaml` (все статусы), бэклогу и архиву изменений; `rejected` без `new_arguments` не добавляется;
- пункт, требующий от владельца действий сверх «Берём», помечается `needs_owner`; команда предпочитает предлагать то, что делается без владельца;
- пункты `planned`, чьё изменение заархивировано, переводятся в `done`.

Работу шага выполняет субагент `mcfly:analyst` (у него есть знание проекта); для поиска в интернете ему нужны инструменты поиска и чтения страниц в headless-прогоне — разрешить в шаблоне прав, если их нет.

Правило в `mcfly-process`: «молчание — согласие» к списку предложений не применяется; пункт без «Берём» никогда не превращается в работу.

### Настройки (`mcfly/config.yaml`, раздел `ideas`)

```yaml
ideas:
  enabled: true                  # false — прежнее поведение 0.6.3 (шаг 2b: планировщик создаёт изменения сам)
  backlog: "SHARED-UNDERSTANDING.md §4.1"   # где бэклог владельца; пусто — только идеи команды и заметки
  per_run: 2                     # новых пунктов за обычный прогон
  per_idle_run: 4                # за прогон без работы
  show: 7                        # пунктов на экране «Предложения»
  research: true                 # искать похожие системы в интернете
```

Значения по умолчанию — как выше, кроме `backlog` (пусто). Для emmett-brown владелец задаёт `backlog` сам (правка `config.yaml` — только владелец).

## Ограничения

- Комплект — личный актив владельца; правки — в сессии с владельцем, не командой. Изменение `config.yaml` проекта и плагина команде запрещено, как сейчас.
- Telegram: `callback_data` ≤ 64 байт; сообщение ≤ 4000 символов (`splitHtml`), список режется по пунктам.
- `ideas.yaml` пишут и бот, и прогон, как `questions.yaml`; запись — тем же способом, что и у вопросов, с тем же уровнем защиты от одновременной записи.
- Квота: шаг «Предложения» тратит квоту Max; потолки выше. Поиск в интернете — только внутри доли времени шага.
- `npm test` остаётся зелёным; новые тесты — на разбор команд и кнопок, вид «Предложений», переходы статусов (включая `discuss` из обоих мест и запрет `rejected` из Telegram), отсутствие авто-одобрения у изменений с `mcfly.idea`, поведение шага 2 по веткам (проверка текста промпта), идею владельца заметкой, `mcfly ideas list|set`.

## На усмотрение исполнителя

- Разметка экрана «Предложения» и формулировки кнопок в пределах примера выше.
- Как именно «ещё» листает (страницы по 7 или «показать все»).
- Где в коде живёт модуль списка (`src/ideas.js` по образцу `questions.js`) и как разделить вид и запись.
- Формат строки нового пункта в отчёте и в «Статусе».
- Миграция: в проекте без `ideas.yaml` файл создаётся при первой записи; `mcfly init` кладёт пустой шаблон и раздел `ideas` в шаблон `config.yaml`.

## Решения сессии (не владельца) — проверить при чтении

- Без `taken` и без одобренных изменений команда **не** планирует новых изменений сама (шаг 2c), а только пополняет список. Так выбор всегда за владельцем.
- `ideas.enabled` по умолчанию `true` для всех проектов: после обновления комплекта команда без «Берём» сама изменения не планирует. Прежнее поведение 0.6.3 — `ideas.enabled: false`; в CHANGELOG — заметным пунктом. (Комплектом пока пользуется один проект — emmett-brown.)
- Взятый пункт при занятой команде планируется в том же прогоне после основной работы, если до дедлайна ≥ 30 минут.
- Перенос бэклога владельца не ограничен потолком 2/4: в первом прогоне — целиком.
- «▶️ Запусти» запускает прогон и тогда, когда одобренной работы нет, но есть пункты `taken`. Прогон без работы и без `taken` (только пополнение списка) — по-прежнему ночью по расписанию и по «запусти всё равно». Его расход — квота подписки Max (не LiteLLM), не больше 25 % времени прогона.
- «Не сейчас» по пункту из списка ведёт себя так же, как отказ плана: пункт → `discuss`, разбор в сессии (владелец ответил про отказ плана; для единообразия сессия распространила это на кнопку в списке).
- Потолки 10 % / 25 % времени и 2 / 4 пункта.
- Идея владельца — по префиксу «идея:» или «💡», чтобы обычные заметки не превращались в пункты.
