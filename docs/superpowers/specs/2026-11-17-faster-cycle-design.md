# Ускорение цикла: число изменений за прогон, быстрый путь, порядок очереди, мелочи без одобрения

Дата: 17–18.11.2026. Версии: 0.16.0–0.16.2 и 0.17.0 (сделано).

## Зачем

Цикл «предложение → Берём → прогон с планом → Одобрить → прогон с работой» оказался слишком долгим для небольших задач. Разбор недели прогонов в двух проектах:
- почти каждый прогон делал ровно одно небольшое изменение (размер S) и готовил один следующий план;
- после этого команда ждала кнопки «Одобрить», владелец нажимал её и сразу «Запусти» — десятки раз подряд за день;
- потолок `limits.max_changes_per_run` почти не достигался: держался один план впереди (`ideas.plan_ahead: 1`), а план по взятому пункту молчанием не одобряется;
- цепочка прогонов не срабатывала: после прогона не оставалось одобренной работы;
- приоритет у изменений был (`mcfly.priority`), но поставить его из бота было нельзя, у взятых пунктов порядка не было;
- отката сделанного не было.

## Решения владельца

1. Без нажатий делаются только **доделки** к уже сделанному: мелкие замечания проверки, уборка и служебное, мелкие правки существующего видимого (формулировка, строка-подсказка, цвет, отступ). Свежие идеи команды, даже мелкие, ждут «Берём».
2. После «Берём» второе одобрение (плана) не нужно для пунктов S и M, которые не меняют видимое. Крупное (L), новые кнопки, экраны, сообщения и изменение поведения — с планом и образцом до работы.
3. О сделанном без одобрения — блок в отчёте и кнопка «Вернуть» на каждый пункт.
4. Ночью до пяти изменений за прогон; на «Запусти» бот спрашивает «1 / 3 / 5» и помнит прошлый выбор.
5. Доделок — до трёх за прогон сверх задач владельца.

Не меняется: одобрение для прода, секретов и платного; запрет команде править настройки проекта и ставить одобрения; пункт без «Берём» не становится работой (кроме доделок из п. 1).

## 0.16.0 — скорость очереди (сделано)

Всё новое включается настройками; без них поведение прежнее.

**Число изменений за прогон.** `maxChanges(cfg, mode, override)` в `src/config.js`: число из запуска → ночью `limits.max_changes_night` → `limits.max_changes_per_run`. Число доходит до промпта и контекста (`limit`), пишется в запись прогона (`max_changes`), наследуется цепочкой. Запуск: `mcfly run --changes N`, «запусти N», кнопки `rn:N` (`rn:N!` — «всё равно»). `limits.run_choices` — варианты кнопок; прошлый выбор — в `mcfly/state.json` (`run_changes`).

**Быстрый путь.** `fastTrackBlock(change, ideaItems, cfg, category)` в `src/approvals.js` возвращает причину отказа или пустую строку. Условия: размеры всех пунктов из `ideas.fast_sizes`; категория с ответом по умолчанию; в плане раздел «Как это будет выглядеть» без образцов; задач не больше `limits.max_tasks_per_change`; план не возвращали (`mcfly.held`). `mcfly approval request --idea` при пустой причине ставит `approved`, `by: fast`. Решает код, а не роль: запрет `approval set` в прогоне остаётся. Страховка — `mcfly approval hold` (разрешён в прогоне, только ужесточает) и правило ревьюеру. Итог прогона: строка «⚡ Без второго одобрения».

Почему раздел с образцами обязателен и для проекта без описания продукта: иначе «не меняет видимое» было бы нечем подтвердить — отсутствие раздела значило бы согласие.

**Порядок очереди.** `moveFirst` (изменения) и `markFirst` / `takenInOrder` (взятые пункты, поле `first_at`). План по поднятому пункту получает наименьший приоритет в `approval request`. Бот: экран «очередь» (`queueView`, `queueKeyboard`), кнопки `up:` и `qu:1`, текст «вперёд I7». В прогоне `approval first` и `ideas first` запрещены.

## 0.17.0 — мелочи без одобрения (сделано)

Поправлено по итогам первой ночи на 0.16: в проекте, где почти всё — тексты и кнопки бота, быстрый путь «снаружи ничего не меняется» подошёл одному плану из семи. Плюс два случая из той же ночи: пункт, работа по которому оказалась не нужна, нельзя было закрыть из бота; возвращённый командой план владелец по привычке одобрил обычной кнопкой.

**Правка существующего видимого** (`ideas.fast_edits`). `visibleBlock` в `src/approvals.js`: образцы в плане допустимы, если в разделе «Как это будет выглядеть» есть строка «Правка существующего: …», а задач не больше `escalation.small_change_max_tasks`; для быстрого пути — только пункты S. Отличить правку от нового код не может: пометку ставит планировщик, сверяет ревьюер (расхождение — `approval hold`), владелец видит результат в итоге прогона и может вернуть. Это осознанный размен скорости на точность; отпечаток плана (0.16.1) и сверка перед слиянием (0.16.2) действуют и здесь.

**Доделки** (`limits.followups_per_run`). `followupBlock`: родитель в архиве, предел за прогон (считается по событиям `changes_followup` с номером прогона), мало задач, категория с ответом по умолчанию, видимое — по `visibleBlock`. `approval request --followup` либо одобряет (`by: followup`, `followup_of`), либо отказывает и ничего не запрашивает — доделка не превращается в план, ждущий одобрения молчанием. Шаг 5b в задании лида.

**Итог прогона и «Вернуть».** Блок «⚡ Без вашего одобрения» собирается из изменений с `by: fast | followup`, одобренных за прогон; под завершёнными — кнопки `rv:<имя>`. Обработчик создаёт взятый пункт с `revert_of` и `first_at`; `fastTrackBlock` для такого пункта не проверяет видимое — владелец уже решил.

**Закрыть без работы.** `closeChange` (отклонено + `closed`) и `closeIdea` (пункт отклонён окончательно — решение владельца, а не «не сейчас»). Контекст прогона перечисляет закрытые, лид убирает их папки в шаге 0.

**Возвращённый план.** `mcfly.held` меняет текст и кнопки: `ap:` — «Всё равно делать», `cl:` — «Закрыть без работы»; `isAutoApprovable` для него ложно.

Не сделано: команда `mcfly approval revert` для сессии — достаточно текста «вернуть <имя>» боту.
