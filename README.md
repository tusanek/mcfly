# mcfly

Комплект «ИИ-команды разработки» на нативном Claude Code. Ставится на любой проект и работает без человека за клавиатурой: ночью команда агентов планирует, пишет код через TDD, проверяет, ревьюит и интегрирует, а утром вы читаете сводку в Telegram и отвечаете на вопросы с телефона.

**Что внутри**

- Плагин Claude Code: десять ролей-субагентов (lead, analyst, architect, planner, developer, tester, reviewer, devops, designer, reporter), скиллы процесса, слэш-команды, хук контекста.
- CLI `mcfly`: ночные прогоны по расписанию launchd (macOS), проверка окна запуска, лимит времени, `caffeinate`, разбор результата, метрики.
- Спецификации на [OpenSpec](https://github.com/Fission-AI/OpenSpec): изменение = proposal + дельты спецификаций + design + tasks. mcfly добавляет флаг одобрения человеком.
- Telegram в обе стороны: утренняя сводка, вопросы с ответом по умолчанию и сроком, одобрения изменений; ответы пишутся в файлы проекта, команда читает их на следующем прогоне.

## Требования

- macOS (launchd, caffeinate), Node ≥ 20, git.
- Claude Code CLI 2.1+ с подпиской (прогон идёт через `claude -p`, agent teams не используются).
- OpenSpec: `npm install -g @fission-ai/openspec@latest`.
- Бот Telegram (создаётся в BotFather).

## Установка

```bash
git clone git@github.com:tusanek/mcfly.git ~/mcfly
cd ~/mcfly && npm install && npm link   # даёт команду mcfly в PATH
```

Быстрый старт по шагам: [docs/quickstart.md](docs/quickstart.md).

## Команды

| Команда | Что делает |
|---|---|
| `mcfly init [--name <проект>] [--with-tracker]` | Создаёт `mcfly/` в проекте, правила в `.claude/settings.json`, раздел в CLAUDE.md, инициализирует OpenSpec |
| `mcfly doctor` | Проверяет окружение и настройки |
| `mcfly run [--mode night\|day] [--dry-run]` | Прогон команды. `night` запускается только в окне слота, иначе фиксирует пропуск |
| `mcfly summary [--send]` | Утренняя сводка: в консоль или в Telegram |
| `mcfly answers` | Забирает ответы из Telegram и применяет их |
| `mcfly context` | Контекст состояния для агентов (его же подмешивает хук SessionStart) |
| `mcfly status` | Состояние проекта |
| `mcfly question add --category <c> --text <t> --default <d>` | Эскалация человеку (используют агенты) |
| `mcfly approval request\|set\|list` | Одобрения изменений OpenSpec |
| `mcfly metric add --key <k> [--value <n>]` | Метрики (используют агенты) |
| `mcfly telegram pair` | Привязка чата |
| `mcfly schedule install\|remove\|status` | Задания launchd: прогоны и сводка |

Общий флаг `--project <dir>`; по умолчанию текущий каталог или `MCFLY_PROJECT_DIR`.

## Файлы состояния в проекте

```
mcfly/
  config.yaml      расписание, лимиты, категории эскалации, Telegram
  .env             MCFLY_TELEGRAM_TOKEN и прочие секреты (в .gitignore)
  progress.md      журнал прогонов и заметки репортёра
  questions.yaml   вопросы человеку: категория, ответ по умолчанию, срок, статус
  answers.md       ответы и заметки человека (пополняется из Telegram)
  runs/<id>/       prompt.md, stdout.log, events.log (живая лента действий, токены замаскированы), result.json
                   (статус, ходы, стоимость, субагенты, незакоммиченные файлы, заметка), validate.json, summary.md
                   (отчёт репортёра или авто-сводка runner'а)
  metrics.jsonl    прогоны и события (задачи, эскалации, возвраты ревью)
  state.json       offset Telegram, время последней сводки
```

## Цикл прогона

1. Runner забирает ответы из Telegram, закрывает просроченные вопросы ответами по умолчанию, авто-одобряет просроченные изменения (кроме категории prod), собирает контекст (изменения с прогрессом по веткам `change/*`, worktree команды, вопросы, ответы, журнал) и запускает `claude -p --agent mcfly:lead` с промптом из `prompts/run.md`. Фоновые задачи в прогоне отключены (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`): субагенты работают синхронно, параллельность — несколько вызовов в одном ходе лида. Токен Telegram агентам не передаётся.
2. Лид смотрит фронт работ: есть одобренные изменения с открытыми задачами → реализация; нет → планировщик создаёт 1–2 изменения и запрашивает одобрение.
3. Разработчики берут по задаче в отдельных worktree (красный тест → зелёный → коммит → `[x]` в tasks.md). Тестировщик проверяет по сценариям дельт, ревьюер делает ревью (не больше двух кругов).
4. DevOps сливает в main, гоняет тесты, архивирует изменение через `openspec archive`, строго по одному.
5. Репортёр пишет `runs/<id>/summary.md`, дополняет журнал, регистрирует метрики. Runner проверяет `openspec validate --all --strict`, незакоммиченные файлы (без своих служебных) и worktree команды с незакоммиченной работой, записывает результат, пишет авто-сводку, если репортёр не отработал, и коммитит только свои служебные пути.

## Эскалации и одобрения

Категории: `spec` (спецификация, критерии приёмки), `deps` (зависимости, платные ресурсы), `prod` (прод-сервер, секреты, доступы), `budget`, `stuck` (два неудачных подхода). Каждый вопрос приходит с ответом по умолчанию и сроком (24 ч); после срока команда действует по умолчанию. Категория `prod` по умолчанию не исполняется никогда, вопрос без ответа по умолчанию допустим только в ней. Предложения изменений: молчание 24 ч = одобрение (кроме prod и неизвестных категорий). Одобрение ставит только человек: в прогоне команды `mcfly approval set` отклоняется, агенты используют `approval request`. Решение человека `approval set` сразу коммитится отдельным коммитом (`chore(<изменение>): одобрение человека — <статус>`), только файл `.openspec.yaml` изменения; если коммит не удался (изменение ещё не в git), метаданные закоммитит ближайший прогон. Это защита от ошибки агента, а не от злого умысла: обойти её можно, убрав `MCFLY_RUN_ID` из окружения или правя `.openspec.yaml` вручную.

Форматы ответов в Telegram:

```
Q3: b                      ответ на вопрос Q3
Q3 свой текст              то же
approve add-cache          одобрить изменение
reject add-cache причина   отклонить
запусти                    запрос ручного запуска (выполняется с ноутбука: mcfly run --mode day)
любой другой текст         заметка для команды
```

## Расписание и пропуски

По умолчанию прогоны в 00:00 и 04:00 до 180 минут, сводка в 08:00. Если Mac был выключен или спал, launchd запустит задание при пробуждении, runner увидит, что окно слота (30 минут) прошло, и запишет пропуск; сводка покажет его и подскажет ручной запуск. Прогон, наткнувшийся на лок другого прогона, записывается как «не запущен (шёл другой прогон)»; лок старше лимита прогона + 30 минут считается брошенным. Сон на время прогона блокирует `caffeinate`; ноутбук должен быть на зарядке.

## Безопасность

`mcfly init` добавляет в `.claude/settings.json` запреты: `git push --force`, `sudo`, `ssh`, `scp`, `launchctl`, чтение `mcfly/.env`, правка `mcfly/config.yaml`. Скилл процесса запрещает команде трогать прод-сервер и секреты, пропускать дельты спецификаций и ослаблять тесты. Токены живут только в `mcfly/.env` и в переменных окружения.

## Модели ролей

Лид работает на модели из `run.model` в `mcfly/config.yaml`; роли planner, architect, reviewer и analyst её наследуют. Роли с рутинной работой (developer, tester, devops, reporter, designer) закреплены за более дешёвой моделью полем `model:` в `agents/<роль>.md`; по умолчанию это `claude-sonnet-5-5`. Чтобы поменять раскладку, правьте эти поля в комплекте.

## Метрики

`mcfly metric` и утренняя сводка: число прогонов по статусам, оценка стоимости, задач закрыто, эскалаций, возвратов с ревью, падений тестов, изменений предложено и завершено.

## Устранение неполадок

- **Нет chat_id**: `mcfly telegram pair`, затем отправьте боту сообщение.
- **Прогон со статусом network**: нет доступа к API. Ответ `403 Request not allowed` значит, что запрос ушёл без VPN (неподдерживаемый регион); бывают и сетевые ошибки. Runner повторяет прогон каждые `run.network_retry_minutes` (10) минут до `run.network_retries` (6) раз в пределах `max_minutes` и, если доступ не появился, сразу пишет в Telegram, не дожидаясь сводки. Включите в VPN-клиенте автоподключение. Прогоны со статусом error тоже сообщаются в Telegram сразу.
- **Прогон со статусом quota**: достигнут лимит подписки; следующий прогон пройдёт по расписанию, либо запустите днём `mcfly run --mode day`. Недельный лимит («weekly limit») роняет все прогоны за секунды до сброса: следите за расходом дневных сессий в тот же аккаунт.
- **«Background tasks still running after 600s; terminating» в stdout.log**: так CLI до 0.3.0 убивал фоновых субагентов после ухода лида в ожидание; с 0.3.0 фон в прогоне отключён. В `result.json` поле `subagents.background` должно быть 0.
- **Пропущенные прогоны**: Mac спал; проверьте зарядку и `mcfly schedule status`.
- **VPN**: прогоны не зависят от VPN, но задачи с внешними системами могут; проектируйте тесты через записанные ответы.
- **401 OAuth access token is invalid при прогоне**: у отдельного CLI устарел токен подписки. Войдите заново в терминале (`claude`, затем `/login`) или получите долгоживущий токен `claude setup-token` и положите его в `mcfly/.env` как `CLAUDE_CODE_OAUTH_TOKEN`. Проверка: `mcfly doctor --probe`.
- **Агент `mcfly:lead` не найден**: проверьте `claude plugin validate ~/mcfly` и значение `run.lead_agent` в `mcfly/config.yaml`.

## Дорожная карта

Watch-режим (команда `запусти` из Telegram запускает дневной прогон сама); проектный навык wrap-up как шаблон в `mcfly init`; перенос на сервер компании; Stop-hook цикл для длинных прогонов; проверка комплекта на втором проекте.

Отложено по ревью 2026-09-29 (причина — в скобках):
- `/mcfly:run` в интерактивной сессии идёт через `--dry-run`: ответы из Telegram не забираются, просроченное не закрывается, прогон не записывается (нужен режим подготовки без запуска claude — отдельное решение);
- тесты CLI вызывают установленные `claude` и `openspec` (заглушки в PATH; на результат пока не влияет);
- пропущенный прогон коммитит служебные файлы, даже если идёт другой прогон (редкий случай: пробуждение Mac во время ручного прогона; после 0.3.0 коммитятся только служебные пути);
- deny-правило `git push --force*` не ловит `git push origin main --force` (команда не пушит; синтаксис шаблонов прав уточнить);
- runner делает слишком много — лок, окно, Telegram, поток событий, git, авто-сводка (разделить при следующей доработке);
- worktree команды в detached HEAD (обрыв посреди rebase) считается чужим и выпадает из «незакоммиченной работы» (редкий случай);
- тесты прогона вызывают установленный `openspec validate` (заглушка в PATH вместе с тестами CLI);
- ветка удаления заданий в `schedule install` не покрыта тестом — вызывает `launchctl` (покрыт отбор меток `staleLabels`, `ownLabels`);
- deny-правила на `.env` закрывают инструменты Read, Edit и Write, но не `cat .env` через Bash и не `.env.local` (синтаксис правил Bash уточнить вместе с правилом force push).
