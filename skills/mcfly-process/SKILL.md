# Процесс mcfly

## Цикл прогона
1. Контекст: runner передаёт лиду состояние (одобренные изменения, ожидающие одобрения, открытые вопросы, ответы человека, журнал).
2. Фронт работ: одобренные изменения с открытыми задачами → реализация. Нет таких → планирование новых изменений и запрос одобрения.
3. Реализация: разработчики по задачам, каждый в своём worktree от Claude Code (раздел «Рабочие копии и ветки»; TDD); тестировщик проверяет по сценариям; ревьюер делает ревью; не больше двух кругов возвратов.
4. Интеграция: devops сливает в main, тесты на main зелёные, архивация при полном выполнении.
5. Завершение: репортёр готовит отчёт, лид записывает его в файлы и коммитит (раздел «Отчёт прогона»); лид убеждается в чистом рабочем дереве.

## Артефакты
- `openspec/specs` — правда о системе; `openspec/changes/<имя>` — единица работы (proposal, дельты specs, design, tasks).
- `mcfly/progress.md` — журнал; `mcfly/questions.yaml` и `mcfly/answers.md` — вопросы человеку и ответы; `mcfly/runs/<id>/summary.md` — отчёты; `mcfly/metrics.jsonl` — метрики (только через `mcfly metric add`, напрямую не редактировать).

## Ворота качества
- Тесты: красный → зелёный для каждой задачи; полный набор зелёный перед слиянием.
- Полный набор тестов проекта запускают только тестировщик (один раз за круг проверки изменения) и devops (на main после слияния). Разработчики и ревьюер запускают только тесты своей задачи и затронутого кода (`-Dtest=…`, свой модуль или пакет). Причина (30.10): набор вырос до ~3500 тестов и 4–5 минут, параллельные разработчики гоняли его десятки раз за прогон и мешали друг другу на одном ноутбуке — прогон шёл 2–3 часа вместо 30–40 минут. Поломку чужих тестов ловит тестировщик.
- `openspec validate <имя> --strict` без ошибок перед запросом одобрения и перед архивацией.
- Ревью: блокеры и «важно» исправлены.
- Коммиты в формате conventional commits; рабочее дерево чистое в конце прогона.

## Эскалации человеку
Категории: spec (спецификация, критерии приёмки), deps (внешние зависимости, платные ресурсы), prod (прод-сервер, секреты, доступы), budget (бюджет, расписание), stuck (два неудачных подхода подряд).
Команда: `mcfly question add --category <кат> --text "<вопрос>" --default "<ответ по умолчанию>"`.
После регистрации продолжайте по ответу по умолчанию. Исключение — prod: остановитесь и ждите явного ответа.
Одобрение изменений: `mcfly approval request <имя>`; человек одобряет в Telegram; молчание 24 часа = одобрение (кроме prod). Ставить одобрение (`mcfly approval set`) может только человек: в прогоне команда отказывает.

Список предложений (0.7.0, `mcfly/ideas.yaml`, кнопка «💡 Предложения»): пополняется только командой `mcfly ideas add`; новое изменение планируется только по пункту, который взял владелец (`mcfly approval request <имя> --idea <Iн>`). К списку правило «молчание — согласие» не применяется: пункт без «Берём» никогда не превращается в работу, план по пункту молчанием не одобряется. Пункты на обсуждении и отклонённые (`discuss`, `rejected`) команда не трогает: решение по ним владелец принимает в сессии (`mcfly ideas set` в прогоне запрещён).
Всё остальное решайте сами и фиксируйте допущение в proposal, design или отчёте.

## Рабочие копии и ветки
Классификатор разрешений Claude Code (headless, режим auto) отклоняет у субагентов переключение и сброс веток (`git checkout`, `git switch`, `git reset --hard`, `git worktree remove`) в worktree, который агент не создавал сам, а Claude Code — любые команды субагента с `cd` в основной checkout. Поэтому схема одна, без вариантов:
- Ветку `change/<имя>` создаёт лид от main: `git branch change/<имя> main`. В основном checkout ветку не выбирают — там всегда main.
- Разработчик (mcfly:developer) работает только в worktree, который Claude Code создаёт сам при запуске агента (`isolation: worktree`): каталог `.claude/worktrees/agent-<id>`, ветка `worktree-agent-<id>` от текущего main. Первая git-команда — `git merge --ff-only change/<имя>`; если main ушёл вперёд и fast-forward невозможен — `git merge --no-edit change/<имя>`. Дальше коммиты в свою ветку. Лиду — имя ветки (`git branch --show-current`) и sha вершины.
- Разработчику запрещено: `git checkout` и `git switch` (в том числе `git checkout change/<имя>`), `git reset`, `git stash`, `git rebase`, `git worktree add` и `git worktree remove`, `cd` в основной checkout или чужой worktree, `git -C <чужой каталог>`. Конфликт при слиянии `change/<имя>` не разрешает — сообщает лиду.
- Лид забирает результат: `git fetch . worktree-agent-<id>:change/<имя>` (только fast-forward, без `+`), затем `git worktree remove .claude/worktrees/agent-<id>` и `git branch -D worktree-agent-<id>`. Если fetch отказал (ветку изменения уже сдвинул другой разработчик), лид сливает в своём временном worktree: `git worktree add <каталог вне проекта> change/<имя>`, `git -C <каталог> merge --no-edit worktree-agent-<id>`, `git worktree remove <каталог>`.
- Разработчика, вернувшегося без коммитов, не продолжают через SendMessage: Claude Code уже удалил его пустой worktree. Запускают нового.
- Тестировщик и ревьюер сами создают себе worktree вне каталога проекта и вне `.claude/worktrees/`: ревьюер — `git worktree add --detach <каталог> change/<имя>`, тестировщик — `git worktree add <каталог> change/<имя>` (тесты коммитит сразу в ветку изменения; разработчиков на этом изменении в это время нет). В конце каждый удаляет свой worktree: `git worktree remove <каталог>`.
- devops сливает `change/<имя>` в main в основном checkout (`git merge --no-ff`), другие ветки там не выбирает.

## Машина владельца
Команда работает на ноутбуке владельца (macOS), а не в изолированной машине. Каждый доступ к чужим данным macOS показывает владельцу окном «Приложение «node» запрашивает доступ…»: прогоны запускает node из launchd, и все их процессы спрашивают от его имени. Окна всплывают посреди работы, а «Разрешить» навсегда открывает node эти данные.
- Поиск файлов — только в своём каталоге работы (worktree), проекте и `/tmp`, всегда с явным каталогом. Не искать по `/`, `~`, `$HOME`, `~/Library`, `/Volumes` (`find`, `grep -r`, `rg`, `ls -R`, `du`, `mdfind`): поиск по всему диску заходит в сетевые тома и данные других программ. 29.10 тестировщик искал свой файл через `find / -name …` — два окна подряд. Свои временные файлы клади в известный каталог и ищи там.
- Docker (`docker`, `docker compose`, `docker images`) — только если задача прямо про образы, контейнеры или скрипты развёртывания. Docker Desktop хранит данные в контейнере другой программы, и каждый вызов может показать окно. Тесты проекта с настоящим Docker — только по флагу проекта, если он есть.

## Отчёт прогона
Claude Code не даёт субагентам записывать файлы отчётов: инструмент Write отвечает «Subagents should return findings as text, not write report files». Поэтому репортёр готовит тексты и возвращает их в ответе, а файлы `mcfly/runs/<id>/summary.md`, строки `mcfly/progress.md` и передачу `mcfly/shifts/…-night.md` записывает и коммитит лид. Метрики репортёр регистрирует сам через `mcfly metric add`.

## Лимиты
Из контекста прогона: время, число изменений за прогон, число задач на изменение. Не больше двух кругов ревью на изменение. При лимите квоты или времени — сразу к завершению.

## Запрещено
Прод-сервер и секреты; `git push --force`; удаление чужих веток; правка `mcfly/config.yaml`, `mcfly/.env` и файлов плагина mcfly; пропуск дельт спецификаций без одобрения; ослабление или удаление тестов ради зелёного прогона.

## Готовность изменения
Все задачи `[x]`, тесты зелёные на main, ревью одобрено, `openspec validate --strict` чист, изменение заархивировано, отчёт написан.

## Передача смены
Файлы `mcfly/shifts/ГГГГММДД-ЧЧММ-day.md` (день → ночь) и `-night.md` (ночь → день). Формат:

    # Смена: день → ночь, <дата время> (источник: человек | команда | авто)
    ## Изменения
    ### <изменение> — ветка change/<изменение> @ <sha>, задач <сделано>/<всего>
    - Где остановились: …
    - Дальше: …
    - Не трогать: …
    ## Порядок            (в ночной передаче — ## Предложение на день)
    1. <изменение>
    ## Нужны решения человека
    - … или «нет» (только шаги вне состояния mcfly — как «Нужно от человека» в отчёте)
    ## Заметки
    - …

«Нужны решения человека» — по правилам раздела «Нужно от человека» отчёта: одобрения, решения по пунктам списка предложений и вопросы сюда не пишутся, их сводка берёт из состояния; решение с ответом по умолчанию — `mcfly question add`. Передача — снимок на конец ночи: сводка не показывает её пункты и «Предложение на день», если после неё прошёл любой прогон.

Передача действует в рамках одобренного: неодобренное не трогать, при расхождении правы одобрения и спецификации. Ветки `shift/*` — дневная работа человека: не трогать, не повторять.
